# Routing — how kernel-set picks a kernel

kernel-set decides "which kernel runs this op" at **three** distinct tiers.
They serve different questions, own different catalogs, and never need to be
unified — this doc is the map.

```
                          a model name                a live op call
                       (deepseek-v3, h100, fp8)     (rms_norm(x, w), gpu, dtype)
                               │                            │
                               ▼                            ▼
        ┌───────────────────────────────┐   ┌────────────────────────────────┐
 Tier 1 │ STATIC PLAN                    │   │ RUNTIME DISPATCH        Tier 2  │
        │ models/select.py  (+ ksctl)   │   │ kernel_set.dispatch +           │
        │                               │   │ backends/_probe + _registry     │
        │ model → per-op kernel-set ABI │   │ op → best *installed* provider  │
        │ symbol + dtype + rationale    │   │ (flash-attn / FlashInfer /      │
        │ "what SHOULD run, and why"    │   │  DeepGEMM / Liger / … )         │
        └───────────────┬───────────────┘   └────────────────┬───────────────┘
                        │ reads                               │ reads
                        ▼                                     ▼
                 models/registry.json              providers/registry.json
                 (model architectures +            (127 ops, ranked providers)
                  default op→fn map)                         │ generates
                        │                                    ▼
                        │                          benchmarks/baselines.yaml
                        │                          (rank-1 baseline per op)
                        ▼                                     │
        ┌────────────────────────────────────────────────────────────────────┐
 Tier 3 │ PORTABLE FALLBACK — kernel-set C ABI (include/kernel_set/*.h)        │
        │ the always-available implementation every tier ultimately routes to; │
        │ its own runtime decides device/dtype support. Dispatch's provider    │
        │ chain ALWAYS ends here, so routing never dead-ends.                  │
        └────────────────────────────────────────────────────────────────────┘
```

## Tier 1 — static model→kernel plan (`models/select.py`, `models/ksctl`)

**Question:** given a *model name* + GPU + dtype + mode, which kernel-set C-ABI
entry point should each logical op use, and *why*?

* **Owns:** the per-op **plan** — the kernel-set ABI symbol (`ks_*`), the
  `ks_dtype_t` to feed it, and a one-line rationale naming the real-world
  best-in-class backend the choice is modeled on.
* **Inputs:** `models/registry.json` (model architecture facts + the default
  op→fn map per model, generated by `models/_gen_registry.py`) plus the GPU
  capability / dtype rules in `models/gpu_caps.json`.
* **Algorithm:** layer GPU-capability + dtype degradation rules on the model's
  default op map (FP8 only sm89+, bf16 needs sm80+, MLA→`ks_mla_decode`, MoE
  adds gate + grouped-GEMM, etc.). Pure stdlib, no GPU, no torch.
* **Surface:** `models/ksctl` — `list` / `plan` / `table` / `backends`. It is a
  *planning / documentation* tool ("what would run on this GPU"), not a runtime.
* **Selects:** one kernel-set ABI symbol per op. It does **not** consider whether
  third-party libraries are installed — that is Tier 2's job.

## Tier 2 — runtime best-available-provider dispatch (`kernel_set.dispatch`)

**Question:** for a *live op call* on this host, what is the strongest kernel
that is actually **installed** right now?

* **Owns:** the rank-ordered provider chain per op and the live selection.
* **Modules (each labeled in its own docstring):**
  * `kernel_set/dispatch.py` — the public API (`rms_norm(...)`, `which(op)`,
    `chain(op)`, `available()`). Walks the chain and calls the first selectable
    provider.
  * `backends/_registry.py` — the curated provider table (ranked providers with
    `min_sm`, `dtypes`, `import_check`, and a *lazy* call adapter per provider).
    **Derived from `providers/registry.json`**, pared to ops with real callable
    providers.
  * `backends/_probe.py` — the gates: import-availability (cached, never raises)
    and arch/dtype support. SM/caps and dtype aliases come from the shared
    `models/gpu_caps.json` (with an inlined fallback for wheel installs).
  * `backends/__init__.py` — re-exports the table + probe helpers.
* **Algorithm:** for an op + (gpu arch, dtype), walk the rank-ordered chain and
  pick the first provider that (a) imports, (b) meets `min_sm`, and (c) supports
  the dtype. Arch-/import-gated providers are skipped silently.
* **Selects:** a concrete installed library call (e.g. `flash-attn`,
  `FlashInfer`, `DeepGEMM`, `Marlin/vLLM`, `Liger`) — or the kernel-set fallback.

## Tier 3 — portable fallback (kernel-set C ABI)

The kernel-set shared library (`include/kernel_set/*.h`, built from
`kernels/src/`) is the always-available implementation. Both upper tiers
ultimately name it: Tier 1 *only* ever selects kernel-set symbols; Tier 2
appends the kernel-set provider to the end of **every** op's chain and treats it
as selectable everywhere, so dispatch never dead-ends on a host with nothing
else installed.

## The catalogs and how they relate

| Catalog | Tier | Role |
|---|---|---|
| `models/registry.json` | 1 | model architectures + default op→fn map (gen by `models/_gen_registry.py`) |
| `models/gpu_caps.json` | 1 + 2 | **single source of truth** for GPU SM/caps + dtype aliases, shared by `select.py` and `_probe.py` |
| `providers/registry.json` | 2 | the merged industry-operator catalog: 127 ops × ranked providers |
| `backends/_registry.py` | 2 | the runnable subset of the above, with lazy call adapters (derived from it) |
| `benchmarks/baselines.yaml` | (bench) | rank-1 baseline per op, **generated** from `providers/registry.json` by `scripts/gen_baselines.py` |
| `docs/OPERATOR_CATALOG.md` | (docs) | the full human-readable ranked per-op catalog |

**Why not one engine?** Tier 1 answers *model → single ABI symbol + rationale*
(a static plan); Tier 2 answers *op → ranked chain of installed providers* (a
runtime probe). They share *facts* (GPU caps, dtype aliases — now via
`models/gpu_caps.json`) but not *algorithms*, and forcing them together would
add an abstraction without removing real duplication. See
[`docs/ARCHITECTURE.md`](ARCHITECTURE.md) for the layered C-ABI / kernel design.
